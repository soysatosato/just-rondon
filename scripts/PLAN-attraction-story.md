# AttractionSection → AttractionStory 移行

`scripts/survey-attraction-sections.ts` の実測にもとづく設計と、実施の記録。

## 進捗

- [x] 調査（`survey-attraction-sections.ts`）
- [x] `AttractionStory` 追加（`20260817000000_add_attraction_story`）
- [x] 移行スクリプト（`migrate-sections-to-stories.ts`）と投入

- [ ] `AttractionSection` の削除 ← **本番で問題がないことを確認してから別コミットで**

`AttractionAccess`（交通手段ごとの分解）は**見送り**。
ファクトバーが現状機能しており、読み物の構造変更と同時にやると
問題が出たときの切り分けが難しくなるため。必要になったら別途。

## いま何が起きているか

`AttractionSection` は135スポットで **1,018節・215,526字**。
`title` が自由文字列なので **172種類の見出し**が生まれ、うち **138種類は1件しか
使われていない**（「アクセス」「アクセス方法」「所在地」「場所」が全部同義）。

この状態だと表示側の判断がすべて正規表現頼みになる。実際、
`isRedundantOverview()` は145件の「概要」に対して **0件** しか検出できていない。

さらに **393節・60,896字が事実の重複**で、ファクトバーと二重になるため
表示側で伏せられている。データとしては生きているが、誰にも読まれていない。

## 新しいモデル

```prisma
/// 観光スポットの読み物。AttractionSection の後継。
///
/// 旧 AttractionSection は title が自由文字列だったため、同じ話題に
/// 172種類の見出しが生まれ、表示側が正規表現で推測する羽目になった。
/// ここでは kind を固定値に限定し、見出しは表示用の飾りとして分離する。
///
/// 事実(料金・アクセス・開館・所要)はここに入れない。カラムと
/// AttractionAccess が持つ。本文に事実を書くと、ファクトバーと
/// 二重になったうえ、改定時に両方直す必要が出る。
model AttractionStory {
  id           Int        @id @default(autoincrement())
  attractionId String
  attraction   Attraction @relation(fields: [attractionId], references: [id], onDelete: Cascade)

  /// "highlight" | "history" | "trivia" | "practical" | "context"
  /// ★自由入力しない。増やすときは表示側の並び順とラベルも同時に直すこと。
  kind         String
  /// 表示用の見出し。null なら kind ごとの既定ラベルを使う。
  /// 「なぜ中世の城のような外観なのか」のような固有の見出しだけ入れる。
  heading      String?
  /// 本文。markdown。MarkdownBody で描画する。
  body         String

  /// 節に添える画像。null 可(写真を自前で撮らない運用のため)。
  imageUrl     String?
  /// "commons" | "official" | "own" 等。表示側の分岐に使う。
  /// URL だけ持っていてもライセンス表記ができないので必ず併せて持つ。
  imageSource  String?
  /// 出典・ライセンス表記。commons のときは必須。
  imageCredit  String?
  imageLink    String?
  /// 画像の下に出す説明。何が写っているかと、本文のどこに効くかを書く。
  imageCaption String?

  displayOrder Int      @default(0)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@index([attractionId, displayOrder])
}
```

### kind の定義

| kind | 既定ラベル | 中身 |
| --- | --- | --- |
| `highlight` | 見どころ | 何を見るか。visitFlow がある場合は表示側で伏せる |
| `history` | 歴史 | 成り立ち、建築、変遷 |
| `trivia` | 豆知識 | 逸話、由来、驚きのある事実 |
| `practical` | 訪問のヒント | 服装、年齢制限、混雑、飲食、ショップ |
| `context` | （個別に指定） | そのスポット固有の話（「跳ね橋の仕組み」など） |

`imageSource` 系を4つ持たせるのは `BrandImage` / `Souvenir` の先例に合わせたため。
Commons の画像は作者名とライセンスの表記が要るので、URL だけでは正しく描けない。

## 事実の受け皿

`facts` 393節の行き先。既存カラムで足りない部分だけ新設する。

```prisma
/// 交通手段ごとのアクセス。
///
/// 既存の nearestStation(String?) は1行しか持てず、84/135しか埋まっていない。
/// 一方「アクセス」節141件の中には、バス86件・船17件・自転車27件の記述がある。
/// 1行に詰め込むと情報が落ちるので、手段ごとに分ける。
model AttractionAccess {
  id           Int        @id @default(autoincrement())
  attractionId String
  attraction   Attraction @relation(fields: [attractionId], references: [id], onDelete: Cascade)

  /// "tube" | "rail" | "bus" | "boat" | "cycle" | "walk"
  mode         String
  /// "Tower Hill (District, Circle) 徒歩5分" のような1行。
  detail       String
  displayOrder Int @default(0)

  @@index([attractionId, displayOrder])
}
```

## 手作業が要る69件

### review 31件（3,386字）

自動分類できなかったもの。「高さと構造」「改修工事」「雨天時の過ごし方」
「試合日のツアー」など、**内容は良いが見出しが独特**なもの。
`kind` を人が決めて `heading` にその見出しを残す。

### 概要の退避候補 38件

「概要」を消す前に、summary に無い**数値を伴う事実**が入っているもの。

- BTタワー「1965年・177m」
- ザ・シャード「68・69階・72階」
- セント・ポール「1666年・1710年・111m・364フィート」
- 自然史博物館「1753年・1881年・8,000万点」

これらは `history` か `trivia` へ退避してから概要を消す。

## 進め方

1. **この計画をレビュー**（いまここ）
2. `AttractionStory` と `AttractionAccess` を追加。**旧 `AttractionSection` は残す**
3. 移行スクリプト（ドライラン既定・`--apply` で投入）
   - 自動分類ぶんを一括投入
   - 69件は個別の割り当て表をスクリプト内に持つ
4. 表示側を `AttractionStory` に切り替え。旧モデルは読まなくなるが**まだ消さない**
5. 本番で問題がないことを確認してから、別コミットで `AttractionSection` を削除

4と5を分けるのは、表示を切り替えた直後に問題が出たときへ戻せるようにするため。
移行スクリプトは冪等にし、何度流しても同じ結果になるようにする。

### 途中で直したこと

計画では事実の節を無条件に捨てる想定だったが、ドライランの結果
**カラムが空のまま節だけ消えるページが78件**あることが分かった
（アクセス46・開館24・料金7・所要1）。
`visibleSections` が元から守っていた「伏せるのは値が入っているときだけ」
というルールを移行スクリプトが踏襲していなかった。
カラムが空なら `practical` として本文に残すよう修正し、
移行対象が503→587節に増えた。

### 投入が途中で切れる問題

接続先が Supabase で遠く、135スポットを1件ずつ処理すると2分を超える。
`--resume` を追加し、既に `AttractionStory` を持つスポットを飛ばして
続きから流せるようにした。途中で切れても同じコマンドで再開できる。

なお `--resume` は**同じロジックで続きを流すため**のもの。
分類ロジックを直したあとは `--resume` を付けずに全件流し直すこと。
付けたままだと、古いロジックで入ったスポットが更新されない。

### 見出しが重複する問題

`heading` を null にすると `kind` の既定ラベルで描かれる。ここで
「ショップ・飲食」まで null にしていたため、ザ・シャードで
「訪問のヒント」が2つ並んだ（practical は守備範囲が広く、
ショップも年齢制限も同じラベルになる）。

null にしてよいのは **既定ラベルと一対一で対応する見出しだけ** に限定した。
`RESCUE` した「概要」も、kind に応じた具体的な見出し（「成り立ち」
「基本情報」など）を与える。

表示側にも保険として `withUniqueHeadings()` を置き、同じ見出しが
並んだ場合は番号を振る。手であとから足したときに気づけるようにするため。

## level 5 の11件を書き直した（2026-08-17）

構造を移しただけでは本文の質は上がらない、というのが移行後に分かったこと。
`scripts/seed-attraction-stories-level5.ts` で11件を書き直した。

移行直後の実測では、**11件で実際に描画されていたのは合計7,638字**しかなかった。
原因は2つある。

1. 旧 `AttractionSection` の本文が、そもそも事実の羅列だった
   （ロンドン塔の「歴史」は年号を並べただけの248字）
2. **11件すべてに visitFlow があるため `highlight` が全部伏せられていた**
   （`visibleStories`）。大英博物館は主要な2節が `highlight` で、
   1,049字のうち383字しか表示されていなかった

書き直しの結果 **21,682字**。`highlight` を1本も作らなかったので、
保有と表示が一致している（伏せられて読まれない本文がゼロ）。

### 書く基準にしたもの

手本は移行前から質が高かったタワーブリッジ。因果を書く・固有名詞と数字を出す・
俗説は訂正する・事実（料金/アクセス/開館/所要）は書かない、の4点。

**`highlight` は原則作らない。** 「何を見るか」は visitFlow が担うので、
story 側は「その場に立ったときに、見えているものの意味が変わる情報」に絞る。
`history` / `context` / `trivia` / `practical` の4本構成で揃えた。

### 裏取りで見つかった誤り

README-visit-flow.md が「level 5 の11件で4件の誤りが見つかった」と記録している
とおり、今回も既存データの誤りが3件出た。

- **カラス伝説はヴィクトリア朝の創作**。塔の公式歴史家 Geoffrey Parnell が
  千年分の記録を精査したが1883年以前に言及がない。チャールズ2世の逸話は
  同時代の裏付けを欠く
- **キーセレモニーは無料**。旧本文の「別チケット要」は誤解を招く。
  有料ではなく、抽選・事前予約で枠が埋まっているだけ
- **スローンのミルクココアは「発明」と言い切れない**。現地で行われていた
  飲み方を学んだ可能性が高いと指摘されている

出典URLはスクリプト冒頭の `SOURCES` コメントに残した。

### マークダウンの太字で5件壊れた

[[markdown-bold-japanese]] の条件（太字の中身が閉じ括弧・鉤括弧・英数字で
終わり、直後が日本語）に9箇所該当し、`**` が生で出る状態だった。
**grepでは判定できない**ので、`remark-parse` + `remark-gfm` で実際にパースし
`mdast-util-to-string` に `**` が残るかで確認した（最終的に太字201箇所すべて正常）。

## 残っている判断

- `kind` は5つで運用開始。`context` が肥大化するようなら
  「食事・ショップ」あたりを `practical` から独立させる
- 画像は当面すべて null。列だけ先に用意した
- 旧 `AttractionSection` と `components/sightseeing/sections.ts` は
  未使用のまま残してある。ロールバック不要と判断できたら削除する
- **level 3 以下の97件は旧本文のまま。** level 5・4 と同じ問題
  （事実の羅列・visitFlow との重複で `highlight` が伏せられる）を抱えている。
  実測は lv3 が63件で表示42,745字/保有58,498字、lv2 が26件、lv1 が8件
