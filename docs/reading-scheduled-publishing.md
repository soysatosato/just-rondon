# 読み物の予約公開 要件

ステータス: **要件合意済み・DB の列だけ追加済み**(2026-10-04)

- 済: `Content.publishedAt` の追加と、既存221行への `createdAt` の写し(マイグレーション `20261004000000_add_content_published_at`)
- 未: それ以外のすべて(読み出し側の切り替え、管理ページ、スクリプトとスキルの変更)

「英国を読む」の3セクション(コラム・イギリス英語・いまのイギリス)について、記事を前もって書き溜め、運営者が管理ページで文章を確認・承認したものだけを、セクションごとに決まった時刻に公開する。

## 1. 背景と現状

- いまは記事作成スクリプト(`scripts/create-column.ts` / `create-british-english.ts` / `create-modern-britain.ts`)を実行した時点で即公開される。公開前に運営者が本番の見た目で読む手段がない。
- `Content.createdAt` が記事の日付として画面と構造化データ(`publishedTime`)に出ている。
- ホスティングは **Vercel Hobby**。cron は1日1回までで、実行時刻は指定から最大1時間ずれる。
- 読み物のページはすべて ISR(`revalidate = 3600`)。

## 2. 記事の状態

| 状態 | 意味 | 読者から |
|---|---|---|
| 下書き | Claude が書いて DB に入れた直後。公開日時は未定 | 見えない |
| 予約中 | 運営者が承認済み。公開日時が未来 | 見えない |
| 公開済み | 承認済みで、公開日時を過ぎた | 見える |

`Content` に **`publishedAt DateTime?`** を1列足し、この1列で3つの状態を表す。

| `publishedAt` | 状態 |
|---|---|
| null | 下書き |
| 未来の時刻 | 予約中 |
| 過去の時刻 | 公開済み |

- 状態を表す列は別に持たない。承認・日付の変更・下書きに戻すの3つの操作は、すべて `publishedAt` の書き換えで済む(承認 = 公開日時を入れる、下書きに戻す = null にする)。
- `createdAt` は「記事を書いた日時」のまま触らない。公開日時を `createdAt` に上書きする案は、列の名前と中身が食い違い、書いた日時も失われるので採らなかった。
- 読者に見せる条件は `publishedAt <= 現在時刻`(null は比較で落ちる)。この条件は1か所にまとめ、各クエリから呼ぶ。
- **画面に出す日付と並び順の基準を、`createdAt` から `publishedAt` に切り替える。** 対象は §5 の各クエリの `orderBy`、前後の記事の比較(`fetchAdjacentContents`)、ハブの新着や「最終更新」、詳細ページのメタデータの `publishedTime`、OG 画像の日付表示など。`createdAt` を記事の日付として使っている箇所は、実装時に洗い出して漏れなく切り替える。
- 既存の行は、マイグレーションで `publishedAt = createdAt` を入れた(2026-10-04 適用済み)。これで、いま公開されている記事の日付も並び順も変わらない。
- **実装時の注意**: 列を足してから実装するまでの間も、いまの作成スクリプトは `publishedAt` に値を入れない。その間に作った行は null になる。実装では、下書きを作れるようにする前に `UPDATE "Content" SET "publishedAt" = "createdAt" WHERE "publishedAt" IS NULL` をもう一度当てる。その時点の null は下書きではなく、写し漏れである。
- 読み物以外のカテゴリ(イベントやクリスマスマーケットなど)も同じ `Content` テーブルにある。これらには予約公開を使わないので、`publishedAt` を見ない。マイグレーションでは値を入れておくが、表示や絞り込みには使わない。

## 3. セクションごとの公開ルール

公開時刻は**ロンドン時間を基準**にする。在住者の生活は現地の時計で動いており、日本側は夏冬で1時間ずれても夕方〜夜の範囲に収まるため。

| セクション | 頻度 | 公開時刻(ロンドン) | 日本(夏/冬) | 承認時の公開日 |
|---|---|---|---|---|
| イギリス英語 | 不定期 | 7:00 | 15:00 / 16:00 | 承認時に運営者が日付を選ぶ |
| いまのイギリス | 不定期 | 10:00 | 18:00 / 19:00 | 承認時に日付を選ぶ。初期値は直近の公開枠 |
| コラム | 毎日 | 12:30 | 20:30 / 21:30 | コラム枠の次に空いている日に自動で入る |

- 時刻を選んだ理由: 日英の両方が起きていて読めるのは「ロンドンの朝〜昼 = 日本の夕方〜夜」だけ。イギリス英語は軽い読み物なので通勤の始まり、いまのイギリスは英国の朝のニュースが出そろった後、コラムは長い読み物なのでロンドンの昼休みと日本の夜のくつろぎ時間が重なる時刻にした。
- 夏時間・冬時間(2026年は10/25に冬時間へ切り替わる)は、承認時に `Europe/London` で計算して吸収する。保存するのは UTC の時刻。
- 枠はセクションごとに独立している。同じ日にコラムとイギリス英語が出てもよい。
- コラムのキューが空になった日は、コラムを休む。
- いまのイギリスは、選んだ公開日が元ニュースの公表から3日を過ぎていれば警告を出す(スキルの「公表から3日以内」の規則を守るため)。そのために、元ニュースの公表日を記事ごとに持たせる必要がある(§8)。

## 4. 管理ページ

- URL の例: `/admin/reading`
- **運営者のアカウントだけ**が開ける。`middleware.ts` の matcher に追加する(いまは必要なパスにしか敷いていないため)。
- 運営者の判断: Clerk の `auth().userId` が環境変数 **`ADMIN_CLERK_IDS`**(カンマ区切り)に含まれるか。
  - 値は本番インスタンスのユーザー ID(Profile の ChelseaToastie)。ローカルの `.env` も本番の Clerk キーを使っているので、同じ ID がそのまま使える。`.env` には 2026-10-04 に追加済み。Vercel にも同じ値を入れる。
  - 権限を DB(`Profile` の列や Clerk の `publicMetadata`)に持たせないのは、API のバグで書き換えられる経路を作らないため。ユーザーネームやメールアドレスは本人が変えられるので使わない。
  - ページを開くときだけでなく、承認・日付の変更・下書きに戻すの各操作のたびにサーバー側で判断する。
  - 運営者でなければ404を返す(管理ページがあることを知らせない)。
  - `.env` に昔の `ADMIN_USER_ID` が残っているが、コードからは使われておらず、値も別の ID。こちらは使わない。
- noindex にし、sitemap にも載せない(`next-sitemap.config.js` の exclude に追加)。
- 画面の構成:
  - **下書き**: セクション名、タイトル、作成日、プレビュー、承認
  - **予約中**: 公開日時の順に並べる。セクションごとの時刻をロンドン時間と日本時間の両方で出す
  - **最近公開した記事**: 直近数本
  - コラムの残りの日数(「あと N 日分」)。少なくなったら目立たせる
- 記事ごとの操作:
  - **プレビュー**: 本番と同じ記事ページに「公開前プレビュー」の帯を付けて表示する。運営者のログイン中だけ見える。ISR のキャッシュを通さずに描画する(例: Next の draftMode)
  - **承認**: §3 のルールで公開日時を決めて予約に入れる。イギリス英語といまのイギリスでは日付を選ぶ欄を出す
  - **日付の変更**(予約中のみ)
  - **下書きに戻す**(予約中のみ)
- 本文の編集は、管理ページには持たせない。修正はチャットで Claude に伝え、Claude が DB を更新する。ブラウザ上での編集は、必要になってから検討する。

## 5. 読者から見えなくする範囲

下書きと予約中の記事は、次のすべてで伏せる。1か所でも漏れると、そこから先に記事が出てしまう。

- 各セクションの一覧と、読み物ハブ(`/reading`)の新着・ランキング・最新1本
- トップページの読み物の枠
- 記事の詳細ページ(URL を直接開いたら404)と OG 画像のルート(`app/og/*`)
- 詳細ページの前後の記事(`fetchAdjacentContents`)。古い記事から見た「次の記事」として出てしまうため
- 人気・週間ランキング(`fetchPopularContents` / `fetchWeeklyPopularContents` / `fetchPopularReadingContents` / `fetchWeeklyPopularReadingContents`)
- 連載コラムの全話一覧(`fetchColumnSeries`)
- スポット詳細の「このスポットが出てくるコラム」(`utils/actions/attractions.ts` の `fetchAttractionColumns`)
- スタンプ帳のおすすめコラム(`lib/stamp-share.ts`)
- 閲覧数の加算(`app/api/views/route.ts`)
- sitemap(`next-sitemap.config.js`)

`Content` を読んでいる箇所は、2026-10-04 時点では `utils/actions/contents.ts`、`utils/actions/attractions.ts`、`lib/stamp-share.ts`、`app/api/views/route.ts`、`next-sitemap.config.js` の5ファイル。どれも `publishedAt <= 現在時刻` の共通条件で絞る(§2)。

## 6. 公開時刻とキャッシュ(Hobby の制約)

- 公開の判定はクエリで行う。時刻が来た瞬間から、データ上は公開済みになる。
- ただし画面に出るのは、各ページの ISR(1時間)が切れたとき。**公開時刻から最大1時間遅れる**ことを許容する。
- Hobby では cron が1日1回までで、時刻も最大1時間ずれるため、3セクションの時刻に合わせてキャッシュを作り直すことはできない。cron は置かない。
- 時刻ちょうどに出したくなったら、Pro にして「1時間ごとに動き、直前の1時間に公開時刻を迎えた記事があればキャッシュを作り直す」cron を1本置く。3セクションと夏冬の切り替えをこの1本でカバーできる。
- sitemap はビルドのときにしか作られない。公開した記事が sitemap に載るのは、次のデプロイから。

## 7. 執筆スキルとスクリプトの変更

- `/add-column`・`/add-british-english`・`/add-modern-britain` で作成した記事は、**下書き**(`publishedAt = null`)として登録する。スクリプトの実行で即公開されることはなくなる。
- スキルの完了報告は「公開しました」ではなく、「下書きに入れました。管理ページで確認してください」にする。
- 修正依頼に応えられるよう、3セクションとも本文を更新するスクリプトを用意する(いまあるのはコラムの `scripts/update-column.ts` だけ)。
- ツイート案には「公開日時(○/○ ○:○○ 日本時間)以降に投稿」と添える。公開前に投稿すると、リンク先が404になる。
- 執筆前の重複チェック(既存記事との題材の重なり)では、下書きと予約中の記事も既存として扱う。
- `/backup-db` は、予約中や下書きの記事も DB にしか本文がないので、登録後は従来どおり実行する。
