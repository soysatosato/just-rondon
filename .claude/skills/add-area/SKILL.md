# /add-area — 「ロンドンの街」の記事をDBに追加する

just-rondon の `/areas` セクション用に、**ロンドンのエリア1つぶんの読みもの**を
1本作成し、本番DB(`Content`/`ContentSection` テーブル、`category: "area"`)に
直接登録する。git の commit/push は一切不要 — DBに1行INSERTするだけで
`/areas` と `/areas/[slug]` に(ISR再検証後、最大1時間以内に)反映される。

刊行ペースは**週2本**。1本あたりの取材が重い(警察と土地登記の数字を実際に
引く)ので、本数より1本の厚みを取る方針で決めている。

## このセクションの立ち位置(最重要)

「エリア」を扱うページはサイトに3つある。役割が被ると検索で食い合うので、
**厳格に分ける**:

|                               | 何のページか           | 読者の問い                       |
| ----------------------------- | ---------------------- | -------------------------------- |
| **`/areas`(ここ)**            | **街そのものの読みもの** | 「この街はどんな街なのか」       |
| `/sightseeing/areas`          | 半日の回遊ルート(6本)  | 「ここをどう歩くか」             |
| `/sightseeing/hotels`          | 宿泊エリアの比較表(13) | 「どこに泊まるか」               |
| `/housing/where-to-live`      | 住まい探しの実務       | 「どこに住むか・どう借りるか」   |

- **`/areas` は住宅地も書く**。観光の3ページは中心部しか扱っていない。
  ブリクストン、ペッカム、ウォルサムストウ、アクトンのように「泊まる場所」でも
  「観光地」でもない街が、この連載の主戦場である。
- **決めるページではなく、読むページ**。比較表を作らない。比較は既存の3ページの
  仕事で、こちらは1つの街を縦に掘る。
- 検索語も分ける。「ロンドン エリア ガイド」「ロンドン 街歩き」は
  `/sightseeing/areas` が持っている。こちらが狙うのは
  **「<街名> 治安」「<街名> どんな街」「<街名> 家賃」**。

## Step 1 — 既存の街を確認する(重複防止)

```bash
node -e '
const { PrismaClient } = require("@prisma/client");
const prisma = new PrismaClient();
(async () => {
  const rows = await prisma.content.findMany({
    where: { category: "area" },
    select: { title: true, engTitle: true, slug: true, tags: true, route: true, createdAt: true },
    orderBy: { createdAt: "desc" },
  });
  console.log(JSON.stringify(rows, null, 2));
  await prisma.$disconnect();
})();
'
```

方角(`tags`)の偏りも見る。サウスが4本続いたら次はノースやウェストに振る。

## Step 2 — 街を選ぶ(ユーザーに選ばせる)

`$ARGUMENTS` に街の指定があればそれを使い、この Step の質問は飛ばす。
無ければ、候補を**3つ**挙げて `AskUserQuestion` でユーザーに選ばせる。
勝手に1つ決めて書き始めてはいけない。

在庫は下の優先順に消化する。**上から順に強い検索需要がある**ので、
気分で下から拾わない。

1. **検索が濃い街(まずここを厚く)** — ブリクストン、ショーディッチ、
   ハムステッド、ノッティングヒル、カムデン、グリニッジ、ペッカム、
   イズリントン、ホワイトチャペル、リッチモンド
2. **在住者が調べる街** — クラパム、ダルストン、ハックニー、
   ベスナル・グリーン、ウォルサムストウ、ストーク・ニューイントン、
   アクトン、イーリング、フィンチリー、ゴルダーズ・グリーン、
   セント・ジョンズ・ウッド、スイス・コテージ、アールズ・コート、
   マイダ・ヴェール、キルバーン
3. **中心部(宿ガイドと相互リンクできる)** — ソーホー、コヴェント・ガーデン、
   メイフェア、ブルームズベリー、マリルボン、パディントン、ベイズウォーター、
   キングス・クロス、シティ、サウスバンク、ウェストミンスター、
   サウス・ケンジントン、チェルシー、ストラトフォード、カナリー・ワーフ
4. **外側と川向こう** — ウィンブルドン、キュー、ハマースミス、フラム、
   パットニー、バタシー、ブラックヒース、ルイシャム、ウーリッチ、
   バーモンジー、トッテナム、ウェンブリー、ハロウ、クロイドン、
   マズウェル・ヒル、ハイゲート、シェパーズ・ブッシュ、
   エレファント&キャッスル、ヴォクソール
5. **街が尽きたら通りと市場** — ポートベロー・ロード、ブリック・レーン、
   コロンビア・ロード、サヴィル・ロウ、デンマーク・ストリート、
   ハーレー街、フリート街、ジャーミン・ストリート

`/beyond-london` が持っている郊外の町(ウィンザー、オックスフォード、
ケンブリッジ、バース、コッツウォルズ、ブライトン、カンタベリー、ヨーク、
エディンバラ、湖水地方、ペンザンス)は**この連載では書かない**。

### 候補は「書けること」を確かめてから出す

候補を出す前に、各案について**その街に固有の転換点が1つ挙げられるか**を
Web検索で確かめる。「賑やかな街です」「多様性のある街です」しか書けない街は、
1本もたない。挙げられなかった案は差し替える。

各選択肢の `description` には、**その街の決め手になる事実**を一言添える
(例: ブリクストン — 1948年にウィンドラッシュ号の乗客が最初に住んだ街。
1981年の暴動の現場で、いまは家賃がランベス区の平均を超えている)。

## Step 3 — 数字と由来を取る(必須)

**この連載の価値は数字と出典にある**。日本語のSERPは2019〜2020年の
旅行ブログと留学エージェントで埋まっていて、公的統計を引いた記事がほぼ無い。
そこだけが勝ち筋なので、以下を毎回実際に引く。

- **治安** — `data.police.uk`(street-level crime API / 月別・種別)、
  および Metropolitan Police の犯罪ダッシュボード。**borough 単位**か
  **ward 単位**かを必ず確認し、本文にもどちらかを書く。
- **家賃・住宅価格** — ONS の private rent 統計、HM Land Registry の
  UK House Price Index。いずれも borough 単位の中央値が取れる。
- **人口構成** — ONS Census 2021(borough / ward)。
- **ゾーンと所要時間** — TfL。所要時間は「どの駅から何分」で書く。
- **地名の由来** — Mills 『A Dictionary of London Place Names』、
  Survey of London、British History Online(`british-history.ac.uk`)。
- **その街固有の歴史** — 区の公文書館、地元図書館の郷土資料、当時の新聞。

数字には**必ず年と出典リンク**を付ける。「家賃は高め」ではなく
「2026年のランベス区の家賃中央値は月£1,8xx(ONS)」と書く。裏が取れない
数字は書かない。

## Step 3.5 — 「なぜこの街はこうなった？」を探す（最重要）

この記事は観光情報の羅列ではなく、1つの街を「なぜこうなったのか」という
物語として読む記事にする。

執筆前に、その街について以下のような「知的好奇心を刺激する事実」を探す。

- 名前からは想像できない地名の由来
- 現在の街並みを決定づけた意外な出来事
- 「もし○○がなかったら、今の街は存在しなかった」と言える出来事
- 鉄道・道路・川・市場・工場・住宅開発などによって街の性格が変わった瞬間
- かつての評判と現在の姿が大きく違う理由
- 現在も残っている過去の痕跡
- 「なぜここにこんなものがあるのか？」と疑問を持てる場所
- 数字を見ると意外なことが分かる事実
- ロンドンの他の地域との違いが、その街の歴史から説明できる事実
- 地元では有名だが、日本語圏ではほとんど知られていないエピソード

単に「有名」「人気」「おしゃれ」「多文化」などの形容詞を探すのではなく、
「なぜ？」と続けて質問できる事実を優先する。

候補を見つけたら、
「事実 → なぜ？ → 背景 → 現在の街」
という因果関係が作れるものを記事の中心に据える。

記事を読み終えた読者が
「へえ、そうだったのか」
「だからこの街はこうなっているのか」
「実際に見てみたい」
と思えることを目標にする。

## Step 4 — 治安の書き方(このセクションの最重要ルール)

治安は読者がいちばん検索する項目で、いちばん事故りやすい項目でもある。

- **「治安が悪い」「危険な街」と断定しない。** 統計の値と、その値が
  どの範囲(borough / ward)・どの期間のものかを示して、判断は読者に渡す。
- **borough の数字を街の数字として書かない。** ランベス区の強盗件数は
  ブリクストンの数字ではない。区の数字を使うなら「区全体では」と明記する。
- **時間帯と場所を限定する。** 「夜のブリクストンは危ない」ではなく
  「金曜夜の駅前は人が多く、スリの届け出がこの区で最も多い通りのひとつ」。
- **「10年前はこうだった」を必ず入れる。** 古い風評を訂正することが
  この連載の価値そのもの。日本語のSERP上位が5年以上前の記事で止まっている
  街ほど、ここで差がつく。
- 人種・民族・移民の集住を治安の説明に使わない。統計と因果を混ぜない。

## Step 5 — 執筆する

### タイトルは「カタカナの街名」で始める(必須)

`/areas/[slug]` の metadata は `title` をそのまま出す。イギリス英語のように
コードが「の意味」を足したりはしない。**タイトルの先頭がそのまま検索結果の
先頭に出る**ので、ここを外すと記事は誰にも届かない。

- **先頭をカタカナの街名にする。** 登録スクリプトが先頭がカタカナでない
  payload を弾く。
- 街名のあとに、**検索意図の語(どんな街 / 治安 / 家賃 / 由来)のどれかを
  先頭30字のうちに置く**。日本語の検索結果で読めるのは全角30字ほど。
- 全体は50字前後。つかみは30字より後ろに置く。

良い例:

```
ブリクストンはどんな街か——1981年の暴動から、家賃が区の平均を超えるまで
ペッカムの治安はいま——強盗件数が5年で半減した街と、まだ残る通り
ハムステッドの家賃はなぜロンドンで最も高いのか——地下鉄が掘れなかった丘
```

悪い例(街名が頭にない / 検索語が無い):

```
1981年、この街で何が起きたか        ← 街名が無い
ブリクストン、変わりゆく街の記録    ← 誰も「変わりゆく」で検索しない
```

### フィールド

- `title`: 上記の規則に従った日本語タイトル
- `engTitle`: **必須**。街の英語名(`Brixton`)。スラッグの元になり、
  カード・詳細・OGカードのバッジにも出る。`Brixton, London` のような
  飾りは付けない
- `summary`: 2〜3文。その街を一言でどう捉えたかと、記事の結論を先出しする
- `mainText`: **使わない**(空にする)。summary の直後にもう一段リード文が
  入ると同じ話を二度読ませることになる
- `borough`: 行政区(`ランベス区`)
- `zone`: ゾーン(`2`、またがるなら `2〜3`)
- `access`: 中心部からの所要時間(`ヴィクトリアから地下鉄で9分`)
- `areaId`(任意): 既存ガイドのエリアid。`lib/hotels/booking-link.ts` の
  `AREA_SEARCH_TERMS` か `components/sightseeing/areas/areas.ts` の
  `areaGuideSlugs` に**同じ綴りで存在するときだけ**入れる。入れると記事の
  末尾に宿の比較と回遊ルートへの導線が出る。対応が無ければ省略する
- `attractions`(任意): この街にある観光スポットの slug の配列。
  `Attraction` に実在する slug でないとスクリプトが止まる。街の中にある
  ものだけを入れる(「地下鉄で15分」は入れない)
- `tags`: **必須**。方角を1つ(跨ぐ街だけ2つ)。正典は `lib/area-taxonomy.ts`
  - `central` / `east` / `north` / `south` / `west`
- `image`: **必須**。Wikimedia Commons(`https://upload.wikimedia.org/...`)の
  パブリックドメインまたは再利用可能ライセンスの画像URL。一覧カードと
  詳細の両方がこの値を見ており、null だとどちらにも画像が出ない。
  - **必ずサムネイルURLを使う**。`.../commons/a/ac/Name.jpg` ではなく
    `.../commons/thumb/a/ac/Name.jpg/1280px-Name.jpg` の形
  - 登録前に `curl -sIL "<URL>" | grep -Ei "^(HTTP/|content-length)"` で
    200 が返ることとサイズを確認する
- `sections`: **4〜6個**。下の骨格に対応させる

### 記事の骨格(節の順番は固定)

読者は節の順番で現在位置を測る(詳細ページが節に通し番号を振る)。
**順番を入れ替えない**。

1. **名前の由来** — 地名が何に由来するか。300〜500字。語源辞典か
   Survey of London を出典に。俗説は「諸説ある」と書く
2. **その街がこうなった経緯** — 転換点を1〜2個。鉄道が通った/通らなかった、
   誰が住むことを許されたか、何の工場が閉じたか。400〜700字。ここが記事の
   背骨で、いちばん長くなる節
3. **いまの数字** — 治安・家賃・人口。Step 3 の統計を年と出典付きで。
   400〜600字。表(Markdown)を使ってよい
4. **歩くならどこか** — 市場・公園・店・建物。400〜600字。`attractions` に
   入れたスポットはここで本文にも書き、飛べるようにリンクをつける。
5. **泊まる・住むなら**(任意) — 既存ガイドで足りるなら省略してよい。
   書くなら「この街を選ぶ人・選ばない人」の条件を1段落

各節は `title`(見出し)、`subtitle`(任意)、`description`(Markdown本文)、
`displayOrder`(0始まりの連番。**書き忘れやすい**)。節ごとに `image` と
`imageSummary`(キャプション)を付けてもよい。

`/column` ほど硬くせず、`/british-english` ほど
ふざけない。数字を扱う節では特に断定を避け、出典に語らせる。

### 画像の使い方

画像は記事の装飾のほかにも、「その場所を見てみたい」と思わせるために使う。

すべての節に画像を入れる必要はない。
記事全体で2〜4枚程度を目安に、文章の流れの中で意味がある場所に差し込む。

特に以下のような画像を優先する。

- その街を象徴する現在の風景
- 歴史の説明を理解するのに役立つ建物・通り
- 「なぜここにこんなものがあるのか？」と思わせる場所
- 現在と過去の違いを感じられる場所
- 実際に歩いてみたくなる市場・通り・公園・建物
- 本文で詳しく説明した事実を、現地で確認できる場所

画像を入れる場所は、各sectionに機械的に割り当てない。
「この画像をここで見せることで、本文の理解または街への興味が増すか？」
を基準に決める。

画像が記事の内容に十分な意味を持たない場合は、無理に追加しなくて良い。

画像検索では、観光写真だけでなく、歴史的建築物、道路、住宅、
市場、駅、公園、記念碑など、その街の成り立ちを伝えられるものを探す。

## Step 6 — 太字が壊れていないか確認する(必須)

CommonMark の right-flanking 規則により、閉じ `**` の直前が句読点・
閉じ括弧で直後が日本語文字だと、`**` が生のまま表示される。この連載は
`**£1,800(ONS)**` のような書き方をしやすく、特に踏みやすい。

投入前に react-markdown で実際にレンダリングして、生の `**` が残って
いないか確認する。既存データの点検は:

```bash
npx tsx scripts/fix-content-markdown-bold.ts --dry
```

## Step 7 — DBに登録する

組み立てたJSONをスクラッチパッド等の一時ファイルに書き出し、リポジトリの
ルートで実行する。

```bash
npx tsx scripts/create-area.ts <一時ファイルのパス>
```

成功すると `Created area entry: /areas/<slug> (id=...)` が出力される。

エラーが出た場合の対処:

- `title must start with the area name in katakana` → Step 5 の規則違反。
  タイトルの頭を街名にする
- `Unknown tag "..."` → 方角は `central` / `east` / `north` / `south` / `west`
- `Unknown attraction slug(s)` → `attractions` の綴り違い。DBで確認する
- スラッグ重複 → `engTitle` を微調整して再実行する

## Step 8 — バックアップを取る(必須)

本文はDBにしか無い。登録できたら必ず実行する。

```bash
npx tsx scripts/backup-db.ts
```

## Step 9 — 完了報告

git の操作(commit, push, branch作成など)は一切行わない。
公開された記事のタイトルと `/areas/<slug>` のURL、引いた統計の出典を
ユーザーに報告する。

## Step 10 — ツイート案を出す

完了報告に続けて、公式X用のツイート案を**4〜5案**書き出す。頼まれなくても
毎回出す。DBには登録しない(下書き登録が要るときだけ `/add-tweets` を使う)。

- **140字以内**。URLを含めた実文字数で数え、各案に字数を添える
- 1行目は見出し **【ロンドンの街】**
- 末尾に記事URL `https://www.just-rondon.com/areas/<slug>`
- 4〜5案は切り口をずらす(地名の由来・効いてくる数字・古い風評の訂正・
  歩くならどこか)。治安の数字を煽りに使わない

字数は目分量で数えず、実測する。

```bash
python3 -c 'import sys; t=sys.stdin.read().rstrip("\n"); print(len(t), "OK" if len(t)<=140 else "NG")' <<'TWEET'
【ロンドンの街】
…本文…
https://www.just-rondon.com/areas/<slug>
TWEET
```
