# /add-tweets — Xの投稿下書きをまとめて作る

just-rondon公式Xアカウント用の投稿文を複数件作成し、`TweetDraft`テーブルに
下書き(`status: "draft"`)として登録する。git の commit/push は不要。
投稿用のAPI連携は無いため、実際にXへ投稿するのは人間 — 登録後は `/tweets`
ページで内容を確認し、コピーしてXに手動投稿する運用。

`$ARGUMENTS` に件数や切り口の指定があればそれに従う。無ければ**5件**作る。

## Step 1 — 既存の下書き・投稿済みを確認する(重複防止)

```bash
npx tsx -e '
import db from "./utils/db";
(async () => {
  const rows = await db.tweetDraft.findMany({
    select: { body: true, category: true, status: true, createdAt: true },
    orderBy: { createdAt: "desc" },
    take: 30,
  });
  console.log(JSON.stringify(rows, null, 2));
  await db.$disconnect();
})();
'
```

直近で使ったネタ・言い回しと同じものを繰り返さない。

## Step 2 — ネタの種類を決める

各ツイートに `category` を付ける。

| category | 中身 |
|---|---|
| `tip` | 耳寄り情報。知らないと損する実用的なコツ(チケットの買い方、割引、穴場の時間帯など) |
| `fact` | ロンドン・イギリスの豆知識、あるあるネタ、文化的な小ネタ |
| `news` | 直近の新規オープン、ストライキ予告、期間限定イベントなど、今だから書ける鮮度のある話題 |
| `question` | 読者に問いかけて反応を引き出す投稿(「ロンドンで一番驚いたことは？」等) |

1回の生成では複数カテゴリを混ぜる(同じ種類ばかりだと単調になりインプが伸びにくい)。

## Step 2.5 — 題材を選ぶ(ここでインプが決まる)

カテゴリ配分より**題材選びのほうが伸びを左右する**。内容が良くても、
タイムラインで足を止めさせる引っかかりが無いツイートは読まれない。

以下の2方針のどちらかに当てはまるネタを優先する。毎回どちらかに寄せる必要はなく、
5件作るなら3〜4件はこの2方針から取り、残りを自由枠にするくらいの比率でよい。

### 方針A — 知名度の高い固有名詞を混ぜる

**毎回1〜2件**は、日本人が既に知っている固有名詞を含むネタにする。
知らない土地の一般論より、知っている名前が入っているほうが目に留まる。
加えて、その固有名詞のファン層(サッカークラスタ等)に届くと、普段リーチしない
層に広がる。

候補ジャンル:

- **サッカー** — アーセナル、チェルシー、トッテナム等のクラブ名、スタジアム、観戦情報
- **王室** — バッキンガム宮殿、衛兵交代、王室行事
- **音楽** — ビートルズ(アビイ・ロード)、来日経験のあるアーティストのロンドン公演
- **映画・ドラマのロケ地** — ハリー・ポッター、007、シャーロック等

固有名詞を出すだけでは足りない。**「実はこうだった」という落差**とセットにする。
例:「アビイ・ロードの横断歩道は1970年に移設されていて、ジャケット写真の場所とは
数メートルずれている」。単なる紹介にせず、知っているつもりの対象の意外な一面を出す。

同じジャンルのネタを2件作った場合、**同日に連投しない**よう完了報告で注意を添える
(クラスタが重複して2件目が伸びないため)。

### 方針B — 日本人観光客向けのタイムリーな話題

「今週・今月これから行く人」に刺さる、期限のあるネタ。締切があるぶん行動を促せる。

- 期間限定イベント、フェス、今週末で終わる展覧会
- ストライキ・大規模運休の予告
- 新規オープン、季節限定の営業時間(夏の延長開館など)
- 予約開始日が迫っているもの(例: オープン・ハウスの予約開始)

**日本人観光客にとって実用的か**で取捨する。ロンドン在住者向けのニッチな地域
イベント(地元の清掃活動、小規模なコミュニティ行事など)は、内容が良くても
観光客には使えないので避ける。

#### 方針Bのネタは Time Out London で探す(省略不可)

**タイムリーなネタを作る回は、必ず Time Out London を見てから書く。**
思いつきや記憶で「今こんなイベントがあるはず」と書かない。

とくに**ニュース欄を最優先で開く。**突発の催し・ポップアップ・企業の
プロモ企画は、イベント一覧のページには載らず**ニュース記事としてのみ出る**。
週次ダイジェストで実際に取りこぼした実例として、タワーブリッジ横で
行われた無料のポケモン謎解きイベント(Potter's Field Park)がある。
こういう「写真が撮れて・無料で・期間が短い」ネタはXと相性が良く、
取りこぼすと痛い。

- `https://www.timeout.com/london/news` — **突発イベントはここ。最優先**
- `https://www.timeout.com/london/things-to-do` — 定番の一覧
- 記事URLは `.../london/news/<スラッグ>-<MMDDYY>` 形式で末尾が日付。
  **直近1〜2週間の記事**を読む(告知は開催の数日〜1週間前に出る)

**告知は事前に出るので、来週・再来週の記事も見る。**Xは「これから行く人」に
届いてこそ意味があるので、**開催後に知っても遅い**。予約が要るもの、
初日に混むものは、開催の数日前に投稿できるよう逆算する。

#### 週次ダイジェストを使い回す

`/add-weekly-brief` で作った直近の号は、方針Bのネタ帳としてそのまま使える。
既に一次ソースで裏を取った項目が並んでいるので、調査を二度やらなくて済む。

```bash
npx tsx -e '
import db from "./utils/db";
(async () => {
  const b = await db.weeklyBrief.findFirst({
    orderBy: { weekStart: "desc" },
    include: { items: { orderBy: { displayOrder: "asc" } } },
  });
  if (!b) { console.log("号がありません"); await db.$disconnect(); return; }
  console.log(b.slug, b.title);
  for (const i of b.items) {
    console.log(` [${i.kind}] ${i.title}`);
    console.log(`   ${i.isFree ? "無料" : i.priceInfo ?? ""} / ${i.venue ?? ""} / ${i.source}`);
  }
  await db.$disconnect();
})();
'
```

**ただし号の文章をそのまま縮めない。**ツイートは1件1つの驚きに絞る形なので、
「無料」「今週末で終わり」「実は〇〇」といった**引っかかりを一点に立てて**
書き直す。号に載せた項目のうち、Xで伸びるのは
**無料・期間限定・写真映え・意外性**のどれかを持つものに限られる。

### どちらにも当てはまらないネタ

イギリス英語の言い回し、パブ文化、あるあるネタなどは引き続き有効だが、
**これだけで5件を埋めない**。上記2方針で大半を埋めたうえでの残り枠として使う。

## Step 3 — 執筆する

**ネタは必ずWebSearchで最新情報を裏取りしてから書く**(「たぶんこう」で書かない)。
検索なしで書けるのは自分の中でも自信のある一般常識レベルの豆知識のみに限る。
特に `news` カテゴリは鮮度が命 — 執筆時点の実際の検索結果に基づくこと。

**日付・料金・会期は一次ソース(主催者・会場の公式)で確認する。**
Time Out などの二次媒体は日付を誤ることがある(実例: グリニッジ・フェアを
「8/23〜24」と誤記、主催者公式では 8/22〜23)。**間違った日付を投稿すると
読者が空振りする**ので、ここは省略しない。

**二次媒体どうしで情報が食い違ったら、裏が取れるまでその題材は使わない。**
件数を埋めるより、誤情報を出さないほうが優先。別のネタに差し替える。

`fact` の豆知識も、固有名詞や数字を含むなら裏を取る。
「実はこうだった」系は落差が魅力なぶん、外すと訂正が効かない。

品質基準:

- **具体的であること**。「ロンドンは物価が高い」のような誰でも言える一般論ではなく、
  「〇〇線の△△駅は実は□□という理由で××」のように、狭くて具体的な事実・エピソードを書く。
- **1ツイート = 1つの驚き/気づき**に絞る。詰め込みすぎない。
- トーンはネタごとに変えてよい。速報・注意喚起系(スト予告、休館など)は丁寧に、
  豆知識・あるある系はカジュアルな口語体(「〜って知ってました？」「〜らしい。」)にするなど、
  内容に合わせて使い分ける。全部を同じ調子で統一する必要はない。
- 日本語で**140字以内**(絵文字・改行・URLも含めて)。絵文字は使っても1〜2個程度に抑え、
  多用しない。
- ハッシュタグは付けない(付けるなら最大1つ、`#ロンドン`程度に留める)。
- 特定の店舗・施設名を出す場合は、閉店・改装などで事実が古くなっていないか注意する。
- **関連する自サイトの記事が実在するなら、流入のためURLを添える**(Step 3.5 参照)。
  ただし無理に紐づけない。関連が薄いのに貼ると、ツイートの信頼と回遊率の両方を下げる。

## Step 3.5 — 自サイトへのリンクを付ける

ツイートは単体で完結させつつ、**題材と実際に対応する記事がサイトにあるなら
URLを添えて流入につなげる**。ここが just-rondon の主要な流入経路のひとつ。

### 必ず実在を確認してから貼る

**URLを推測で書かない。**スラッグは英語タイトルから生成されており、
思い浮かべた綴りと一致しないことが多い。DBで実際のスラッグを引く:

```bash
npx tsx -e '
import db from "./utils/db";
(async () => {
  const q = process.argv[1] ?? "";
  const rows = await db.content.findMany({
    where: { OR: [
      { title: { contains: q } },
      { summary: { contains: q } },
    ] },
    select: { title: true, slug: true, category: true },
    take: 20,
  });
  console.log(JSON.stringify(rows, null, 2));
  await db.$disconnect();
})();
' <検索したい語>
```

静的ページ(`/sightseeing/...`、`/housing/...` など DB を持たないセクション)は
`app/(with-ads)/` 配下に実際にディレクトリがあるかで確認する。

URLは `https://www.just-rondon.com` + パスの形にする(`lib/seo.ts` の `SITE_URL`)。
カテゴリごとのパスは `/column/<slug>`、`/modern-britain/<slug>`、
`/british-english/<slug>`、週次ダイジェストは `/events/week/<slug>`
(`/events/<slug>` ではない。最新号は `/events` にも同じ内容で出る)。

### 貼る基準

- **題材が記事の中身と実際に重なっているとき**に貼る。ツイートで触れた事実の
  「続き」や「背景」がその記事にあること。カテゴリが同じなだけでは足りない。
- **1ツイートにつきURLは1本**。複数貼ると本文が読まれない。
- **全件に貼る必要はない**。5〜6件作るうち、自然に紐づくものだけでよい。
  該当が2件なら2件でよく、埋めるために関連の薄い記事を探しにいかない。
- `question` カテゴリには**基本つけない**。返信を集めるのが目的なので、
  リンクがあると読者がタイムラインから離れて反応が落ちる。

### 字数

URLもX上では文字数を消費する(t.co短縮後で概ね23字相当)。
**URLを付ける場合は本文を115字以内**に収め、合計140字を超えないようにする。
登録スクリプトは本文の字数しか見ないので、ここは自分で調整する。

### 書き方

本文の末尾に改行して置く。「詳しくはこちら」のような常套句は付けず、
**本文が終わったところに自然に置く**。煽り文句を足すと広告に見える。

```
9月のテムズ川は1ヶ月まるごとお祭りです。Totally Thamesは1〜30日で100以上の催し、
その約8割が無料。
https://www.just-rondon.com/events/week/2026-w35
```

## Step 3.7 — 登録前のチェック

1つでも「いいえ」があれば Step 2.5 に戻る。

- [ ] 方針Bのネタを含む回なら、**Time Out London のニュース欄**を見たか
- [ ] タイムリーなネタの**日付・料金を一次ソースで**確認したか
- [ ] 開催日・予約開始日から逆算して、**投稿が間に合う**ネタか
      (開催後に届くものは意味がない)
- [ ] 二次媒体どうしで矛盾したまま書いた項目が無いか
- [ ] 全件140字以内か(URL付きは本文115字以内か)
- [ ] 貼ったURLは**DBまたは実ファイルで実在を確認**したか(推測で書いていないか)
- [ ] 関連が薄いのに流入目当てで貼った記事が無いか

## Step 4 — JSONを組み立てて登録する

スクラッチパッドに配列形式で書き出す。

```json
[
  { "body": "ロンドンの地下鉄、実は駅によってホームの位置が路線ごとにバラバラ。乗り換えで一番歩かされるのはグリーン・パーク駅らしい。", "category": "fact" },
  { "body": "大英博物館、実は入場無料なのに寄付ボックスにいくら入れるべきか毎回悩む。目安は1人£5〜10って知ってました？", "category": "tip" },
  { "body": "ロンドンで一番「まさか」だった値段、何でした？私はパブの一杯が£8超えてたことです。", "category": "question" }
]
```

登録する。

```bash
npx tsx scripts/create-tweets.ts <一時ファイルのパス>
```

140字を超える項目があるとスクリプト側でエラーになるので、その場合は該当項目を削って
再実行する。

## Step 5 — 完了報告

git の操作(commit, push, branch作成など)は一切行わない。
最後に以下をユーザーに報告する。

- 登録した件数とカテゴリ内訳
- 各ツイートの本文(全文)
- 投稿タイミングの注意(あれば) — 同じジャンルの固有名詞ネタが複数あるなら日を
  空けること、予約開始日や開催日が迫っているネタはいつまでに出すべきか
- 確認・投稿は `/tweets` ページから行うことを案内する
