# /add-british-english — イギリス英語の項目をDBに追加する

just-rondon の `/british-english` セクション用に、イギリス英語ならではの
単語・言い回し・スラングを1本作成し、本番DB(`Content`/`ContentSection`
テーブル、`category: "british-english"`)に直接登録する。git の
commit/push は一切不要 — DBに1行INSERTするだけで `/british-english` と
`/british-english/[slug]` に(ISR再検証後、最大1時間以内に)反映される。

## Step 1 — 既存項目を確認する(重複防止)

まず既存の `category: "british-english"` のタイトル・英語表現・スラッグを
全件取得し、今日選ぶ表現が既出と重複しないか確認する。

```bash
node -e '
const { PrismaClient } = require("@prisma/client");
const prisma = new PrismaClient();
(async () => {
  const rows = await prisma.content.findMany({
    where: { category: "british-english" },
    select: { title: true, engTitle: true, slug: true, createdAt: true },
    orderBy: { createdAt: "desc" },
  });
  console.log(JSON.stringify(rows, null, 2));
  await prisma.$disconnect();
})();
'
```

### 予約済みスラッグを避ける

`/british-english/` 配下には静的ルートが同居しており、同名のスラッグを付けると
Next.js が静的ルートを優先するため、**記事に一生アクセスできなくなる**
(一覧にカードは出るのにクリックすると別ページが開く)。

現在の予約語: **`scenes`**(場面別フレーズ集)

新しい静的ルートを足したときはここに追記する。実際の予約語は
`app/(with-ads)/british-english/` 直下のディレクトリ名で確認できる:

```bash
ls -d "app/(with-ads)/british-english"/*/ | xargs -n1 basename | grep -v '^\[slug\]$'
```

選んだ表現のスラッグがこれに当たる場合は、`scenes-slang` のように
接尾辞を付けて衝突を避ける。

## Step 2 — 表現を選ぶ(ユーザーに選ばせる)

`$ARGUMENTS` に表現の指定があればそれを使い、この Step の質問は飛ばす。
無ければ、候補を**3つ**挙げて `AskUserQuestion` でユーザーに選ばせる。
勝手に1つ決めて書き始めてはいけない。

候補を作るときの条件:

- 単語帳の1エントリで終わらせず、**掘り下げがいのあるもの**を選ぶ。
  切り口の例:
  - アメリカ英語と意味・使い方が食い違い、旅行者が誤解しやすいもの
    (例: `first floor`、`pants`、`chips`)
  - 語源に歴史的なエピソードがあるもの(コックニー・押韻スラング、
    軍隊・海事用語からの転用、階級・方言に由来するものなど)
  - 会話に頻出するのに教科書に出てこないもの(相槌、婉曲表現、
    皮肉・アンダーステートメントの言い回し)
  - 地域や世代で使われ方が割れるもの(ロンドンっ子と地方、若者言葉と
    そうでない言葉)
- **3案は切り口の系統をずらす**(全部が語源ネタ、全部が米英ズレ、に
  しない)。ユーザーが「今日はこの方向」で選べるようにする。
- Step 1 で確認した既出の表現とは重複させない。似た系統(相槌表現、
  食べ物がらみのスラング等)が続きすぎないよう、テーマにも変化をつける。

各選択肢の `label` には**英語表現そのもの**を置き、`description` に
「何が面白いか」を一言で書く(例: `fortnight` — 「2週間」と訳すと
半分しか分からない。生き別れた兄弟 `sennight` の話ができる)。

## Step 3 — 下調べして、つかみの方向性を選ばせる

表現が決まったら、**先に Web 検索で語源・用法を裏取りする**。ここで
事実を掴んでから切り口を出すこと(調べる前に方向性を決めると、
裏が取れずに書き直しになる)。

そのうえで、記事の**つかみ・切り口の候補を3つ**挙げて
`AskUserQuestion` でユーザーに選ばせる。各案は「どこから記事に入るか」を
具体的に書く。例:

- よくある場面から入る(ゴミ収集・給料・予約など、その語が実際に
  効いてくる瞬間。誰かの体験談にはせず、旅行者や住人なら誰でも
  出くわす場面として書く)
- 出典のある実例から入る(報道・議会・番組・広告・調査などで、その語が
  実際に使われた一文)
- 語源・歴史から入る(消えた関連語、由来のエピソード)
- 日本語との非対称から入る(同じ概念があるのに使用頻度が違う、等)

### 体験談は作らない(重要)

場面やエピソードは、**「よくある場面」か「出典のある実例」のどちらか**で
書く。書き手や知人の体験談は書かない。

- **書かないもの:** 「僕/私が〜した」「同僚に〜と言われた」「ロンドンの
  友人から聞いた話」「知人が実際に経験した」のような特定の誰かに起きた
  出来事と、「ロンドンに長く住んでいると」のような書き手の経歴。記事の
  名義は「ジャスト・ロンドン編集部」で、こうした体験は確かめようがない。
  作った体験談は書き手を偽ることになる(Google は作成者のプロフィールの
  捏造を欺瞞として扱い、AdSense もパブリッシャーについての不実表示を
  禁じている)。
- **よくある場面:** 旅行者や住人なら誰でも出くわす状況として書く。
  主語は「あなた」「旅行者」か省略にして、「〜すると」「〜されたら」で
  運ぶ。「先日」「この前」のような日付や、名前・続柄のある登場人物は
  出さない。例: 「企画書を出して上司に `quite good` と返されたら、
  喜ぶのはまだ早い」
- **出典のある実例:** 報道・議会の議事録(Hansard)・番組・広告・看板・
  世論調査・辞書の用例など、その語が実際に使われた一文。**本文のその文に
  出典のリンクを付ける**(イギリス英語のページには参考資料欄が無い)。
  引用は原文を短くそのまま載せて日本語の意味を添え、言葉も発言者も
  変えない。リンク先で確かめられなかった例は使わない。
- 既存の記事には、2026-10-27 より前に書いた作った体験談が多く残っている。
  文体の参考に既存記事を読むときも、そこは真似しない。

場面を使う場合は、**「その語を知らなかったせいで困った」という筋書きが
本当に成立するかを検証してから書く**。成立しないなら場面を諦め、語源や
実例から入る。

- 例: `fortnight` を「隔週給で給料をもらい損ねる」場面にするのは無理が
  ある。雇用条件は契約書に書かれているし、実際に人を困らせるのは
  「隔週サイクルの起点がどこか」であって単語の意味ではない。
  **語の理解ではなく別の要因で起きた失敗を、語のせいにしない。**
- 無理なら `mainText` は省略してよい(任意項目)。場面を無理に作るより、
  セクション1の冒頭を語源や事実から始めるほうが良い記事になる。

## Step 4 — 執筆する

品質基準: **「検索で来た人がまず答えを持ち帰れて、読み進めると一個賢くなる」**
ページにする。

2026年11月に全42本を書き直したときの型がこれ。検索から来る読者の問いは、
ほぼ全部「chuffed 意味」「posh 語源」の形をしている(Search Console)。以前の
記事は芸人調のつかみと体験談から入り、意味は最初の節の途中まで出てこなかったため、
10位前後に出てもクリックされていなかった。記事ページは
「英語の語(大)→ title → summary → 早わかり(keyPoints)→ 本文」の順に描かれる
(`components/british-english/BritishEnglishDetail.tsx`)。

### 語り口

- 答えを先に言う。例文を必ず入れる(3〜4個。英文は `` `…` `` で囲み、——のあとに和訳)
- 軽く読める口調はよいが、笑いは事実の上に置く。たとえ話(日本の職場や日常)は
  1記事に1つまで。意味の説明より目立たせない
- 次の決まり文句は書かない: 「ここからが本題」「面白いのは」「結論はシンプル」
  「〜って知ってた?」「日本人がほぼ全員やらかすやつ」。煽りの見出しも避ける
- 語源の俗説は「〜という説がよく紹介されるが、裏付けはない」と書く。確かめられた
  年代・用例には、本文のその文に出典のリンクを付ける(参考資料欄は無い)。
  Etymonline は自動取得を拒むので、検索結果の要約か Wiktionary・Merriam-Webster・
  World Wide Words・Phrase Finder・Green's Dictionary of Slang で確かめる
- 書き手や知人の体験談は書かない(Step 3)。場面は「〜と言われたら」「〜すると」で
  誰にでも起きる形にする

### engTitle は「検索される形」で書く

このセクションに来る検索語は、GSCの実測ではほぼ全部が
`<単語> 意味` か `<単語> 語源` の形をしている。詳細ページの metadata は
`${engTitle} の意味 ｜ ${title}` を組み立てるようになっていて
(`app/(with-ads)/british-english/[slug]/page.tsx`)、
**engTitle がそのまま検索結果の先頭に出る**。

- **人が検索窓に打つ形そのままにする**。原形・小文字が基本
  (`chuffed`、`take the piss`、`quite good`)。
- **活用や飾りを付けない**。`I'm chuffed to bits` ではなく `chuffed`。
  疑問符や引用符も、表現自体に不可欠でないかぎり付けない。
- タイトル側で「意味」「語源」を名乗る必要はない(コードが付ける)。
  ただし `title` は「つかみ」だけにせず、**意味の答えを先頭に置く**(下記)。

以下の構成で記事を組み立てる:

- `title`: 日本語タイトル。**意味の答えを先頭に、続けて一番の要点を1つ**。
  h1 では英語の語の下にこの題が出て、検索結果では `${engTitle} の意味 ｜ ${title}` になる。
  35〜45字が目安。
  - 例: 「すごく嬉しい」のくだけた言い方。辞書に「不機嫌」とも載っている理由(chuffed)
  - 例: イギリスでは「家庭的で居心地がいい」、アメリカでは「器量がよくない」(homely)
  - 例: half seven は7時半。ドイツ語の「halb sieben(6時半)」と1時間ずれる
- `engTitle`: 対象の英語表現そのもの(必須。スラッグ生成に使う。上記の規則で)
- `summary`: 2〜3文。**1文目で「◯◯は「…」という意味の、イギリスのくだけた言い方です」と
  答える**。2文目以降で使い方の勘所か、誤解されやすい点を1つ。検索結果の説明文にもなる
- `keyPoints`: **必須**。「早わかり」の表になる(`Content.description` に入る)。
  各項目を `**ラベル**: 値` の形で書くと、ラベルと値の表で描かれる
  (`lib/reading-keypoints.ts`)。**全項目をこの形にそろえる**(1つでも崩れると箇条書きになる)
  - 必ず入れる: `**意味**`(英米で違うなら `**意味(英)**` `**意味(米)**`)、`**場面**`
  - よく入れる: `**よく使う形**`(英語の形を `` `…` `` で)、`**返し方**`、`**注意**`、`**由来**`(1文)
  - 3〜5項目。値は1〜2文
- `mainText`: **原則使わない**(省略する)。summary と早わかりの直後にもう一段リードが入ると
  同じことを三度読ませることになる
- `sections`: **2〜3個**
  1. 意味と使い方 —— 例文3〜4個、返し方、言い換え、英米差。見出しは内容が分かる短い一文
     (例:「happy より一段上の「嬉しい」」)、`subtitle` は「意味と使い方」
  2. 由来 —— 記録で確かめられる最初の用例・年代、通説と裏付けの有無。`subtitle` は「由来」
  3. (任意)似た言い方・反対の言い方 —— 既存の語へは `[gutted](/british-english/gutted)` の
     ようにサイト内リンクを張る
  - 各セクションは `title` / `subtitle`(任意) / `description`(Markdown、1節400〜700字) /
    `displayOrder`(0始まり)
- `image`(任意): テーマに関連する、Wikimedia Commons
  (`https://upload.wikimedia.org/...`)上のパブリックドメインまたは
  再利用可能ライセンスの画像URL。適切な画像が見つからなければ省略してよい
  (UI側でnull安全に処理される)。
  - **原本の幅が1200px以上のファイルに限る。** Google Discover が大きな
    画像のカードを出す条件で、満たさないと登録スクリプトが理由つきで弾く。
    肖像画などで大きい版が無いときは、関係する場所・建物・物の写真に替える。
    幅は Commons のファイルページか、API
    (`prop=imageinfo&iiprop=size`)で確かめる
  - 原本のURLをそのまま渡してよい。登録スクリプトが1280px版のURLに
    置き換えて保存する(`scripts/lib/article-image.ts`)

## Step 5 — DBに登録する

組み立てたJSONをスクラッチパッド等の一時ファイルに書き出す。登録する前に、
作った体験談が紛れ込んでいないかを機械的に確かめる。

```bash
grep -nE "僕|俺|私が|私は|私の|うちの|筆者|同僚|友人|友達|知人|先日|この前" <一時ファイルのパス>
```

当たった行を読み、書き手や知人の体験として書いていれば、Step 3 の
「よくある場面」か出典のある実例に直す。英語の例文の和訳に出てくる
「私」は直さなくてよい。

問題がなければ、リポジトリのルートで以下を実行してDBに直接登録する。

```bash
npx tsx scripts/create-british-english.ts <一時ファイルのパス>
```

成功すると `Created draft british-english entry: /british-english/<slug> (id=...). Review and approve it at /admin/reading`
が出力される。

**記事は下書きとして入る。** この時点では公開されず、一覧にも記事URLにも
sitemapにも出ない。運営者が管理ページ `/admin/reading` でプレビューして
承認すると、セクションごとの公開時刻(ロンドン時間。コラム 12:30 毎日 /
イギリス英語 7:00 不定期 / いまのイギリス 10:00 不定期)に予約される。
仕組みは `lib/publish-schedule.ts`、要件は `docs/reading-scheduled-publishing.md`。

投入に使ったJSONは消さずに残しておく。プレビューを読んだ運営者から修正を
頼まれたら、そのJSONを直して次で上書きする(下書き・予約の状態は変わらない)。
JSONが手元に無ければ、先に `npx tsx scripts/update-reading.ts export british-english <slug> <出力先.json>`
でDBの今の中身を書き出し、それを直す。

```bash
npx tsx scripts/update-reading.ts british-english <JSONのパス> <slug> --dry   # 差分の確認
npx tsx scripts/update-reading.ts british-english <JSONのパス> <slug>
```

公開済みの記事を直すと、記事の上に「更新」の日付が付き、JSON-LD の dateModified と
sitemap の lastmod もその日になる(`revisedAt`)。表記の統一・誤字・リンク切れのように
読者にとって中身の変わらない直しには `--minor` を付けて、更新日を動かさない。

スラッグ重複エラーが出た場合は原因を確認し、engTitleを
微調整して再実行する。

## Step 6 — 完了報告

git の操作(commit, push, branch作成など)は一切行わない。
最後に、登録した記事のタイトル、slug、参照した主な出典を報告し、
「下書きに入れました。管理ページ(/admin/reading)でプレビューして承認してください」
と伝える。「公開しました」とは書かない(まだ公開されていない)。

## Step 7 — ツイート案を出す

完了報告に続けて、公式X用のツイート案を**4〜5案**書き出す。ユーザーに
頼まれなくても毎回出す。**1案目は王道の要約**(記事の結論をひと言で)にし、
それだけを `/tweets` に下書き登録する(この Step の最後)。残りの案は
チャットに出すだけで、DBには入れない。投稿は人が `/tweets` からコピペで行う。

- **140字以内**。URLを含めた実文字数で数え、各案に字数を添える
- 1行目は見出し **【本日のイギリス英語】**
- 末尾に記事URL `https://www.just-rondon.com/british-english/<slug>`
- 記事は下書きなので、投稿は管理ページで承認して公開日時が来てから。
  それより前に投稿するとリンク先が404になる。案の前にその旨を一言添える
- 4〜5案は切り口をずらす(王道の要約・意外な数字・ありがちな失敗・語源など)。
  ツイートでも、書き手や知人の体験談にはしない

字数は目分量で数えず、実測する。

```bash
python3 -c 'import sys; t=sys.stdin.read().rstrip("\n"); print(len(t), "OK" if len(t)<=140 else "NG")' <<'TWEET'
【本日のイギリス英語】
…本文…
https://www.just-rondon.com/british-english/<slug>
TWEET
```

### 王道の要約を `/tweets` に登録する

1案目だけをスクラッチパッドの JSON に書き出して登録する。`category` は
セクション名(`british-english`)にする。本文の改行は `\n` で書く。

```bash
npx tsx scripts/create-tweets.ts <JSONのパス>
```

```json
[{ "body": "【本日のイギリス英語】\n…本文…\nhttps://www.just-rondon.com/british-english/<slug>", "category": "british-english" }]
```

記事が下書き・予約中のあいだ、`/tweets` はこのツイートを「記事の公開待ち」に
分けて公開日時を出す。管理ページで記事をボツにすると、このツイートも
不採用になる。
