# /add-british-english — イギリス英語の項目をDBに追加する

just-rondon の `/british-english` セクション用に、イギリス英語ならではの
単語・言い回し・スラングを1本作成し、本番DB(`Content`/`ContentSection`
テーブル、`category: "british-english"`)に直接登録する。git の
commit/push は一切不要 — DBに1行INSERTするだけで `/british-english` と
`/british-english/[slug]` に(ISR再検証後、最大1時間以内に)反映される。

## Step 1 — 既存項目を確認する(重複防止)

まず既存の `category: "british-english"` のタイトル・英語表現・スラッグを
全件取得し、今日選ぶ表現が既出と重複しないか確認する。

```bash
node -e '
const { PrismaClient } = require("@prisma/client");
const prisma = new PrismaClient();
(async () => {
  const rows = await prisma.content.findMany({
    where: { category: "british-english" },
    select: { title: true, engTitle: true, slug: true, createdAt: true },
    orderBy: { createdAt: "desc" },
  });
  console.log(JSON.stringify(rows, null, 2));
  await prisma.$disconnect();
})();
'
```

### 予約済みスラッグを避ける

`/british-english/` 配下には静的ルートが同居しており、同名のスラッグを付けると
Next.js が静的ルートを優先するため、**記事に一生アクセスできなくなる**
(一覧にカードは出るのにクリックすると別ページが開く)。

現在の予約語: **`scenes`**(場面別フレーズ集)

新しい静的ルートを足したときはここに追記する。実際の予約語は
`app/(with-ads)/british-english/` 直下のディレクトリ名で確認できる:

```bash
ls -d "app/(with-ads)/british-english"/*/ | xargs -n1 basename | grep -v '^\[slug\]$'
```

選んだ表現のスラッグがこれに当たる場合は、`scenes-slang` のように
接尾辞を付けて衝突を避ける。

## Step 2 — 表現を選ぶ(ユーザーに選ばせる)

`$ARGUMENTS` に表現の指定があればそれを使い、この Step の質問は飛ばす。
無ければ、候補を**3つ**挙げて `AskUserQuestion` でユーザーに選ばせる。
勝手に1つ決めて書き始めてはいけない。

候補を作るときの条件:

- 単語帳の1エントリで終わらせず、**掘り下げがいのあるもの**を選ぶ。
  切り口の例:
  - アメリカ英語と意味・使い方が食い違い、旅行者が誤解しやすいもの
    (例: `first floor`、`pants`、`chips`)
  - 語源に歴史的なエピソードがあるもの(コックニー・押韻スラング、
    軍隊・海事用語からの転用、階級・方言に由来するものなど)
  - 会話に頻出するのに教科書に出てこないもの(相槌、婉曲表現、
    皮肉・アンダーステートメントの言い回し)
  - 地域や世代で使われ方が割れるもの(ロンドンっ子と地方、若者言葉と
    そうでない言葉)
- **3案は切り口の系統をずらす**(全部が語源ネタ、全部が米英ズレ、に
  しない)。ユーザーが「今日はこの方向」で選べるようにする。
- Step 1 で確認した既出の表現とは重複させない。似た系統(相槌表現、
  食べ物がらみのスラング等)が続きすぎないよう、テーマにも変化をつける。

各選択肢の `label` には**英語表現そのもの**を置き、`description` に
「何が面白いか」を一言で書く(例: `fortnight` — 「2週間」と訳すと
半分しか分からない。生き別れた兄弟 `sennight` の話ができる)。

## Step 3 — 下調べして、つかみの方向性を選ばせる

表現が決まったら、**先に Web 検索で語源・用法を裏取りする**。ここで
事実を掴んでから切り口を出すこと(調べる前に方向性を決めると、
裏が取れずに書き直しになる)。

そのうえで、記事の**つかみ・切り口の候補を3つ**挙げて
`AskUserQuestion` でユーザーに選ばせる。各案は「どこから記事に入るか」を
具体的に書く。例:

- 生活の場面から入る(ゴミ収集・給料・予約など、その語が実際に
  効いてくる瞬間の観察)
- 語源・歴史から入る(消えた関連語、由来のエピソード)
- 日本語との非対称から入る(同じ概念があるのに使用頻度が違う、等)

### 体験談を作るときの制約(重要)

つかみに体験談を使う場合、**「その語を知らなかったせいで失敗した」
という筋書きが本当に成立するかを検証してから書く**。成立しないなら
体験談を諦め、観察や語源から入る。

- 例: `fortnight` を「隔週給で給料をもらい損ねた」話にするのは無理が
  ある。雇用条件は契約書に書かれているし、実際に人を困らせるのは
  「隔週サイクルの起点がどこか」であって単語の意味ではない。
  **語の理解ではなく別の要因で起きた失敗を、語のせいにしない。**
- 無理なら `mainText` は省略してよい(任意項目)。作り話で埋めるより、
  セクション1の冒頭を観察から始めるほうが良い記事になる。

## Step 4 — 執筆する

品質基準: **「サクッと読めて、笑えて、でも一個だけ賢くなる」**ページに
する。教科書的な解説記事ではなく、**歯に衣着せず言い切る芸人が
イギリス英語について喋っている個人ブログ・コラム**をイメージする。
単なる和訳と例文の羅列や、講義のような解説は避ける。
また、AI特有の無難で抽象的な文章にならないよう、具体的な事実や背景、印象に残るエピソードを積極的に盛り込む。必要に応じてエピソードは補完・創作し、単なる情報の羅列ではなく、読んでいて情景が浮かぶ、読み応えのある内容にする。

執筆時は「ロンドンで長く暮らしている30代の日本人男性」という視点や経験を活かし、現地で生活しているからこそわかる感覚や具体的な場面を織り交ぜる。ただし、一人の人間があらゆる出来事を直接経験しているようにはせず、本人の体験だけでなく、「ロンドンの友人から聞いた話」「知人が実際に経験した出来事」なども自然に取り入れる。エピソードの出どころに幅を持たせることで、無理に本人の体験談に寄せず、リアリ　　　　　ティのある文章にする。

### トーンの作り方(最重要)

- **「〜と言える」「〜のである」で終わる論文体は禁止**。「〜な気がする」
  「〜だと思う」「〜らしい」のような、軽くて断定的な言い切りで進める。
  ふわっとした言い回しに見えて、中身は鋭く核心を突く——というのが理想。
- 一見関係ない例え・比較・時事ネタ・日本の日常あるあるを持ち込んで
  笑わせる**飛躍**を1箇所以上入れる(例: 英会話の遠回しな言い方を、
  会社の人事評価や合コンの断り文句に例える、など)。飛躍は突飛でよいが、
  最終的には元の英語表現の理解に着地させること。
- 権威的な前提(「ネイティブは〜」「イギリス人は礼儀正しいから〜」)を
  一度は茶化す・疑ってみせる。物わかりの良い解説者ではなく、
  斜に構えて「それってつまりこういうことでは?」と切り込む視点。
  ただし内容の正確性は落とさない——ボケた上で正しいことを言う。
- 「え、それ知らなかったら普通に恥かくのでは」くらいの煽り・
  ツッコミを要所に挟んでよい。読者に語りかける口調(「〜って知ってた?」
  「これ、日本人がほぼ全員やらかすやつ」など)も歓迎。
- テンポ重視。一文を短く切り、無駄な前置き(「さて、〜について
  見ていこう」等)は書かない。結論やオチを先に言ってから理由を
  続けるくらいがちょうどいい。

Step 3 の裏取りで足りない部分は、追加でWeb検索して事実確認しながら書く。
Step 3 でユーザーが選んだつかみの方向性に従って構成すること。不確かな語源の
俗説(いわゆる folk etymology)は、通説として紹介する場合でも「諸説あり」
「有力な説の一つ」など事実として断定しない書き方にする——ただし
「〜らしいが、正直ちょっと怪しいかもしれない」くらいのくだけた言い方に
崩してよい。事実確認の精度は下げない。

### engTitle は「検索される形」で書く

このセクションに来る検索語は、GSCの実測ではほぼ全部が
`<単語> 意味` か `<単語> 語源` の形をしている。詳細ページの metadata は
`${engTitle} の意味 ｜ ${title}` を組み立てるようになっていて
(`app/(with-ads)/british-english/[slug]/page.tsx`)、
**engTitle がそのまま検索結果の先頭に出る**。

- **人が検索窓に打つ形そのままにする**。原形・小文字が基本
  (`chuffed`、`take the piss`、`quite good`)。
- **活用や飾りを付けない**。`I'm chuffed to bits` ではなく `chuffed`。
  疑問符や引用符も、表現自体に不可欠でないかぎり付けない。
- タイトル側で「意味」「語源」を名乗る必要はない。コードが付けるので、
  `title` は**つかみに専念してよい**。

以下の構成で記事を組み立てる:

- `title`: 日本語タイトル(オチや煽りが効いた、思わず開きたくなるもの。
  例:「イギリス人の"quite good"を真に受けると人生を損する」)
- `engTitle`: 対象の英語表現そのもの(必須。スラッグ生成に使う。例:
  `quite good`)。**検索結果のタイトルの先頭にも出る**ので、下記を守る
- `summary`: 1〜2文の要約(結論やオチを先出しして、続きを読ませる
  フック。「実はこう使われている」で終わらせず、ひとこと煽りを添える)
- `mainText`: 会話の一場面や自分のズッコケ体験から始める、ユーモアの
  ある短いつかみ(任意)。Step 3 の制約により体験談が成立しないと
  判断したら、**無理に入れずに省略する**。省略する場合はセクション1の
  冒頭を、つかみを兼ねた導入にする
- `sections`: **1個もしくは2個**。長い解説記事ではない。
  - 各セクションは
    - `title`: 見出し(煽り気味でよい)
    - `subtitle`: 一言(任意)
    - `description`: Markdown形式の本文。**1セクションあたり
      日本語で300〜500字程度**を目安に、短く小気味よくまとめる
      (箇条書きも積極的に使ってテンポを出す)
    - `displayOrder`: 0始まりの連番
- `image`(任意): テーマに関連する、Wikimedia Commons
  (`https://upload.wikimedia.org/...`)上のパブリックドメインまたは
  再利用可能ライセンスの画像URL。適切な画像が見つからなければ省略してよい
  (UI側でnull安全に処理される)。

## Step 5 — DBに登録する

組み立てたJSONをスクラッチパッド等の一時ファイルに書き出し、リポジトリの
ルートで以下を実行してDBに直接登録する。

```bash
npx tsx scripts/create-british-english.ts <一時ファイルのパス>
```

成功すると `Created british-english entry: /british-english/<slug> (id=...)`
が出力される。スラッグ重複エラーが出た場合は原因を確認し、engTitleを
微調整して再実行する。

## Step 6 — 完了報告

git の操作(commit, push, branch作成など)は一切行わない。
最後に、公開された項目のタイトルと `/british-english/[slug]` のURLおよび参照した主な出典をユーザーに報告する。
