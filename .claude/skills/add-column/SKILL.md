# /add-column — コラムをDBに追加する

just-rondon の `/column` セクション用に、イギリスに関するコラムを1本作成し、
本番DB(`Content`/`ContentSection`テーブル、`category: "column"`)に直接登録する。
git の commit/push は一切不要 — DBに1行INSERTするだけで `/column` と
`/column/[slug]` に(ISR再検証後、最大1時間以内に)反映される。

## Step 1 — 既存コラムを確認する(重複防止)

まず既存の `category: "column"` のタイトル・スラッグを全件取得し、
今日選ぶテーマが既出と重複しないか確認する。

```bash
node -e '
const { PrismaClient } = require("@prisma/client");
const prisma = new PrismaClient();
(async () => {
  const rows = await prisma.content.findMany({
    where: { category: "column" },
    select: { title: true, slug: true, tags: true, seriesName: true, seriesOrder: true, createdAt: true },
    orderBy: { createdAt: "desc" },
  });
  console.log(JSON.stringify(rows, null, 2));
  await prisma.$disconnect();
})();
'
```

## Step 2 — テーマを選ぶ(ユーザーに選ばせる)

`$ARGUMENTS` にテーマの指定があればそれを使い、この Step の質問は飛ばす。
無ければ、候補を**3つ**挙げて `AskUserQuestion` でユーザーに選ばせる。
勝手に1つ決めて書き始めてはいけない。

候補を作るときの条件:

- イギリスに関する**狭くて具体的で、意外性のある一つのテーマ**にする
  (歴史、語源、制度、伝統、文化、豆知識など)。
- 「観光ガイド」ではなく「コラム／読み物」として成立するものにする。
- Step 1 で確認した既出テーマとは重複させない。**似た系統が続きすぎない
  ようにも気を配る**(儀式ネタ・都市インフラ・制度の由来などが3本続くと
  セクション全体が単調になる)。既出の傾向を見て、手薄な系統から拾う。
- **そのテーマを検索する人が打つ語を、1つ書き出せること**。書き出せない案は
  候補にしない。2026年9月にGSCで実測したところ、コラム41本のうち
  **34本が検索語をひとつも拾えていなかった**。読み物として面白くても、
  誰も打たない語しか含まない記事には検索から人が来ない。
  ここで書き出した語は、あとで Step 3 のタイトルに使う。
- 「イギリスの歴史」のような広すぎるテーマは避け、深掘りできる粒度に絞る
  (例: 「なぜ英国議会の議事堂には靴のサイズを測る印がある」「バッキンガム宮殿の
  衛兵交代の"儀式"は実は19世紀の実務上の理由から始まった」等、具体的に一段掘り
  下げたテーマ)。
- **3案は系統をずらす**。`tags` の分類(history / person / institution /
  daily / city)が全案で同じにならないようにすると、選ぶ側が
  「今日はこの方向」で判断しやすい。

### 候補は「書けること」を確かめてから出す

コラムは1本が長いので、**史料が薄いテーマを選んでしまうと執筆中に
行き詰まり、手戻りが大きい**。候補を提示する前に、各案について
Web検索を1〜2回かけ、**固有名詞・年月日・数字・引用が取れそうか**を
確かめる。裏が取れそうにない案は候補から外し、別の案に差し替える。

各選択肢の `label` にはテーマを短く置き、`description` には
**「何が意外なのか」と「決め手になる具体的な事実」**を一言添える
(例: バンク・ピケット — 1780年の暴動を機に193年間、近衛兵が毎晩
銀行へ通った。廃止を問われた大臣の答弁が「1780年以来襲われていない」)。

決め手となる事実が出てこないテーマは、それ自体が「薄い」というサインなので
候補にしない。

## Step 3 — 執筆する

品質基準(ユーザーの言葉そのまま):
**「読んでいて勉強になるような詳しくて知的好奇心をくすぐるものにする」**

AIにありがちな薄い列挙型の記事にせず、具体的な事実・背景・エピソードを
盛り込んだ、読み応えのある長文にする。

Step 2 の下調べは「書けるかどうか」を判断するための当たりを付けただけなので、
**ここで改めて本格的に調べる**。一次資料(公文書・議事録・公式アーカイブ)に
当たれるものは当たり、固有名詞・年月日・数字・引用は必ず裏を取る。年代の
前後関係など、本文で因果や皮肉として書く部分は**特に確認する**
(「Aの数週間後にBが起きた」と書くなら両方の日付を確認してから書く)。

### タイトルは先頭30字で決まる

日本語の検索結果でタイトルとして読めるのは**全角30字ほど**で、それ以降は
切り捨てられる。ここを外すと、どれだけ引きの強い一文を書いても、
検索結果には「引き」だけが出て「何の話か」が出ない。

2026年9月に既存41本を実測したときは中央値62字・最長79字あり、
**全本とも固有名詞か年号が30字の外に落ちていた**。同月に全本を書き換えた。

- **先頭30字のうちに、固有名詞か西暦を必ず1つ置く**。人名・地名・建物名・
  制度名・年のいずれか。読者が検索窓に打つのはこれで、引きの一文ではない。
- **パンチのある一文は削らない。固有名詞のあとに移すだけでよい**。
  「引き → 主語」を「主語 → 引き」に入れ替える操作で、面白さは落ちない。
- 全体は**55字前後**まで。連載の「第N回」は末尾でよい(検索結果には出ないが
  サイト内の一覧では効く)。
- 書き終えたら **`title.slice(0, 30)` を実際に目で見て確認する**。
  そこに固有名詞か西暦が無ければ書き直す。

```
✗ 「サリズベリーの人間が買うべきだと思った」——1915年、ストーンヘンジは競売に
   かけられ、椅子を買いに来た男が6,600ポンドで落札した
   → 検索結果に出るのは「「サリズベリーの人間が買うべきだと思った」——1915年、ス」
     まで。肝心のストーンヘンジが消える。

○ 1915年、ストーンヘンジは競売にかけられた——椅子を買いに来た男が6,600ポンドで
   落札し、3年だけ所有した
```

過去の書き換えの対応表は `content/column/title-rewrite-2026-09.json` にある。
実例として参照してよい。

以下の構成でコラムを組み立てる:

- `title`: 日本語タイトル
- `engTitle`: 対応する英語タイトル(任意。スラッグ生成に使われるので付けるのが望ましい)
- `summary`: 2〜3文の要約(読者の興味を引く導入)
- `mainText`: 本編に入る前の短いリード文(任意)
- `sections`: **4〜6個**。各セクションは
  - `title`: 見出し
  - `subtitle`: 一言(任意)
  - `description`: Markdown形式の本文。表層的でない、具体的な内容にする
  - `displayOrder`: 0始まりの連番
  - `image`(任意): その節の写真。形式は下の `image` と同じ
- `image`(任意): 記事の顔になる写真。**URLではなくWikimedia Commonsの
  ファイル名で指定する**。URL・作者・ライセンスは登録スクリプトが
  Commons の API で解決する(CC の画像は作者名とライセンスの表示が条件
  なので、URLだけを書くと表記の無い画像が公開されてしまう)。
  適切な画像が見つからなければ省略してよい(UI側でnull安全に処理される)。

  ```json
  { "commonsFile": "File:Penny black.jpg", "caption": "1840年のペニー・ブラック。国名がどこにも刷られていない。" }
  ```

  - `commonsFile`: `File:` から始まるCommonsのファイル名。パブリック
    ドメインまたは再利用可能ライセンスのものに限る。
  - `caption`(任意): 写真の下に出る説明。「何が写っているか」ではなく
    **「その写真が本文のどの主張を裏付けるか」**を書く。
  - ヒーローは**横位置**の写真を選ぶ(表示側で16:9相当に切り抜くので、
    縦長だと被写体の頭が落ちる)。節の写真は縦位置でもよい。
  - 節の写真は**その節が名指ししている物**にする。別の節の写真を置くと
    意味が反転するので、迷ったら付けない。
- `tags`: **必須**。`/column` のテーマ絞り込みに使う。下記から1〜3個選ぶ。
  ここに無い値を入れると登録スクリプトがエラーで弾く
  (正典は `lib/column-taxonomy.ts`)。
  - `history` — 歴史・事件
  - `person` — 人物
  - `institution` — 王室・制度
  - `daily` — 暮らし・技術
  - `city` — ロンドンの街
- `seriesName` / `seriesOrder`(任意): 連載コラムのときだけ**両方セットで**指定する。
  - `seriesName`: 連載名。同じ連載の全話でこの文字列を完全に一致させる
    (例: `"クリストファー・レン物語"`)。表記が1文字でも違うと別連載になる。
  - `seriesOrder`: 第何回か。1始まりの整数。同じ連載内で重複するとエラーになる。
  - 単発コラムでは**両方とも省略する**。`/column` では2本以上揃った連載だけが
    「連載で読む」欄にまとまり、詳細ページに前後の回へのリンクが出る。

## Step 4 — DBに登録する

組み立てたJSONをスクラッチパッド等の一時ファイルに書き出し、リポジトリの
ルートで以下を実行してDBに直接登録する。

```bash
npx tsx scripts/create-column.ts <一時ファイルのパス>
```

成功すると `Created column: /column/<slug> (id=...)` が出力される。

エラーが出た場合の対処:

- スラッグ重複 → タイトル(または`engTitle`)を微調整して再実行する。
- `Unknown tag "..."` → `tags` に正典外の値が入っている。Step 3 の一覧から選び直す。
- `Series "..." already has 第N回` → その連載の同じ回が既に登録済み。
  Step 1 の出力で `seriesOrder` を確認し、正しい回数に直す。

## Step 5 — 完了報告

git の操作(commit, push, branch作成など)は一切行わない。
最後に、公開されたコラムのタイトルと `/column/<slug>` のURL、および参照した主な出典をユーザーに報告する。
